## 3. Что делает существующий код

### Подготовка и мастер

`Setup-XRS-Templates.cmd`, `scripts/setup-wizard.cjs`, `scripts/lib/setup-core.cjs`
уже реализуют preflight Windows/Node/gh/git, стандартный `gh auth login --web`,
раздельные Ed25519 root/test/stable, проверку пар и key ID, Windows ACL,
проверку отдельного физического USB-носителя, AES-256-GCM/scrypt backup root,
передачу Secrets по stdin и продолжение частичной настройки.

Root private key не записывается отдельным PEM-файлом; backup зашифрован.
Временные test/stable PEM защищаются ACL до записи и удаляются по завершении
соответствующего этапа. Это не шифрование PEM на диске; для новой схемы
необходимо отдельно проверить хранение после аварийного завершения.
Очистка строк JavaScript не гарантирует стирания всех копий из памяти.

Мастер пока блокируется на недоступных API, создаёт одноразовый PR публичного
root и не включает Stable. Его проверка прав не проверяет точное соответствие
вошедшего пользователя ID 210672295; это нужно добавить для выбранной модели
единственного издателя. Комментарий setup-core про OWNER как organization
устарел относительно фактического типа `User`.

### Штатная публикация

`publish-catalog.yml` запускается через workflow_dispatch на main, выполняет
тесты и validate, требует provisioning flag и review соответствующего
Environment. `approval-record.cjs` получает автора подтверждения из GitHub API.
`publish.cjs` читает предложения только из `incoming/` рабочего checkout.
Следовательно, нынешняя передача редакции требует сначала включить файл
предложения в main. Это и создаёт зависимость каждой редакции от PR.

Издатель повторно проверяет baseVersion/baseSha256, поля, размер/структуру,
медицинское подтверждение, роли ключей, сохраняет подписанную историю редакций,
повышает версию/sequence и выпускает `.xrszip`. `release.cjs` запрещает повторное
использование тега, проверяет digest загрузки и публичные SHA-256.
Операционной команды отзыва существующей редакции пока нет. Ошибка после
публикации Release требует диагностики; автоматического безопасного повторения
всей публикации с idempotency receipt пока нет.

### Клиент XRS

`TemplateAdmin`: локальный PIN/Draft, проверка шаблонного источника, экспорт
`.xrsproposal`; `publish()` возвращает PUBLISHER_NOT_CONFIGURED.
Локальное редактирование и административная подготовка используют существующий
редактор/метаданные, но их действия ещё не объединены в общий workflow.

`TemplateUpdateService`/`TemplateCatalogStore`: подписи, SHA-256, совместимость,
подтверждённый план, кэш пакетов, атомарное переключение поколений, история,
откат, high-water защита от replay и сохранение Revoked. Эти механизмы
переиспользуются. Обновления применяются к источнику новых документов.
Локальные overrides хранятся отдельно и сохраняют приоритет; интерфейс
сравнения локальной редакции с новым централизованным шаблоном пока отсутствует.

`rotateRoot` проверяет следующий номер и пороги старого/нового root. Однако
сервис обновления не загружает, не проверяет и не сохраняет цепочку новых
корней. Верификатор ротации не равен готовому механизму её доставки/восстановления.
Безопасную доставку нужно завершить до производственного включения.

## 4. Минимальная архитектура

Отдельный сервер для упаковки и подписания не требуется: эти операции остаются
в защищённом GitHub Actions. Обычная передача шаблона может обходиться без PR
и записи в main. Остаётся обязательная задача: GitHub должен удостоверить
администратора и его отдельное разрешение на конкретную публикацию.

Предлагается отдельный локальный административный процесс на Windows-компьютере
владельца, связанный с XRS через ограниченный IPC. Это не сервер клиники/VPS.
Он использует официальный GitHub CLI, а не встроенный PAT или private App key.
Один раз владелец проходит официальный вход; credentials допускаются только в
Windows Credential Manager под его отдельным Windows-профилем. Обычный клиент
врача, renderer, настройки XRS и proposal не получают GitHub credentials.

GitHub CLI может сохранять токен открытым файлом, если secure store недоступен.
Поэтому простого успешного `gh auth status` недостаточно: будущая реализация
обязана доказать использование защищённого хранилища и заблокировать fallback
к открытым credentials. При невозможности достоверной проверки такую схему
нельзя активировать. Не использовать `gh auth token` в пользовательском выводе.
Точные возможности Windows Credential Manager и права user OAuth на review
проверяются интеграционным испытанием, не предполагаются доказанными.

Владелец согласовал этот вариант после аудита при условии однократного входа
и отсутствия ежедневных операций с GitHub. Альтернатива — GitHub App Device Flow с
краткоживущим user token только в RAM: не нужен сервер, но после завершения
сессии нужен новый официальный вход. Такой UX ранее отклонён. Если оба способа
неприемлемы, следующий вариант для согласования — минимальный локальный
посредник с Windows-аутентификацией в сети клиники; он также не устраняет
необходимость настоящего GitHub user grant для required reviewer.

### Передача предложения без PR

1. Администратор выбирает библиотечный шаблон. XRS сохраняет проверенный
   неизменяемый снимок с медицинским подтверждением, base hash и каналом.
   Открытый протокол пациента не является источником.
2. Административный процесс проверяет OS-пользователя, текущий GitHub user ID,
   права на репозиторий и разрешённый канал. IPC принимает только фиксированные
   команды публикации, без произвольных URL, команд shell или GitHub API.
3. Через GitHub Git Data API создаётся временная data-only ветка запроса с
   предложениями и receipt; PR не создаётся. В main файлы не записываются.
   Перед отправкой явно предупреждать, что репозиторий публичный: после загрузки
   данные могут стать публичными. Автоэвристики не доказывают отсутствие ПДн.
4. workflow_dispatch на main получает точные commit SHA, request ID, SHA-256
   снимка, канал и ожидаемую базовую редакцию. Он читает только разрешённые
   data blobs через API. Запрещено выполнять/checkout код ветки предложения,
   брать из неё workflows, scripts, root или конфигурацию зависимостей.
5. Валидатор без signing secret повторно проверяет данные и текущую подписанную
   базу; готовит неизменяемый receipt. Значения из dispatch не интерполируются
   напрямую в shell. Проверяются лимиты и отсутствие неожиданных файлов.
6. XRS показывает владельцу канал, будущую версию, изменения, результат проверок,
   hash снимка и workflow SHA. Отдельное подтверждение владельца вызывает штатный
   API review pending deployment именно этого run/Environment. Никакого bypass,
   скрытого автоподтверждения или доверия одному PIN.
7. Только после review job получает channel signing secret. Проверка привязки
   approval/receipt/run SHA/hash и повторная проверка базы предшествуют подписи.
   Выдаётся реальный опубликованный номер после проверки публичных файлов.
8. Повторный request ID с тем же hash возвращает прежний результат; с другим
   hash отклоняется. База, изменившаяся после проверки, блокирует публикацию.
   Конкурентные публикации сериализуются. Частично опубликованный Release
   блокирует автоматический retry до безопасного восстановления.

Права административной учётной записи: Contents write для data staging,
Actions write/read для dispatch/status, Deployments write для review — с
учётом фактической модели token. Setup-права на Secrets/Variables используются
отдельно при первоначальной настройке, а не нужны всем врачам. Избыточные scope
GitHub CLI и их хранение должны быть явно проверены до принятия схемы.
Installation token/bot сам по себе не заменяет user context владельца.

### Первоначальная настройка и публичный корень

Переиспользовать ключи/ACL/backup/resume PR №2. Не создавать новые ключи на
повторном запуске. Однократный PR с кодом инфраструктуры/публичным root относится
к изменению инфраструктуры (операция A), а не к каждой редакции шаблона (B).
Он не даёт разрешения обходить main, требовать второго аккаунта без проверки
реальных правил или self-approve PR. При блокирующем правиле требуется отдельное
решение владельца; мастер сообщает точную причину и не меняет защиту.

Первый trust anchor подтверждается владельцем вне недоверенной загрузки и
встраивается в проверенную сборку XRS. SHA-256 корня связывает мастер и сборку.
Просто скачать root.json и довериться ему нельзя. Дальнейшие подписанные
последовательные переходы корня доставляются отдельным публичным набором
метаданных, проверяются до использования и сохраняются атомарно; нужны тесты
expiry, отзыва, пропуска версии, повреждённой цепочки и отката после обновления
root. Приватный root остаётся только в зашифрованной резервной копии.

### Клиенты врачей

Сохранить существующую строку настроек, updater каталога и отдельную версию.
Перед установкой показать изменения и запросить подтверждение. Локальную
редакцию не перезаписывать; при конфликте сохранить её по умолчанию и дать
сравнение, принятие удалённой версии с backup или сохранение локальной.
Обновление каталога не меняет открытые/сохранённые протоколы и updater EXE.
Серверная проверка прав выполняется GitHub, а не видимостью кнопок или PIN.

   [branch protection](https://github.com/002-421/XRS-Templates/settings/branches),
   [Variables](https://github.com/002-421/XRS-Templates/settings/variables/actions).
   Ожидаемый результат — read endpoints доступны авторизованному мастеру и
   совпадают с защищённой политикой. Не отправлять токены/ключи в чат.
3. После реализации и проверки этапа B отдельно разрешить запуск мастера с
   созданием production keys; сейчас его не запускать ради снятия блокировки.
4. После code review отдельно решить merge инфраструктуры/корня. Далее пройти
   test-публикацию и два Windows экземпляра; только затем отдельно согласовать
   первый Stable-каталог. Ни одно из этих согласований не получено этим аудитом.

ветке с синтетическими fixtures; защита и production runtime не менялись.
