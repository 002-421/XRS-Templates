# Simplified Publishing v1 — кандидат этапа B

**Общий статус: BLOCKED для рабочего процесса из XRS.**
Этап A выполнен; backend этапа B реализован и испытывается отдельно от main.
Однократный официальный GitHub login согласован владельцем. Разрешения на
merge, production keys, изменение защиты и Stable-публикацию не предоставлены.

## Что реализовано в этой ветке

- Существующий Windows-мастер принимает только официальную авторизацию
  пользователя `002-421`, ID `210672295`, с `tokenSource:keyring`.
  Открытый hosts.yml, токен в переменных окружения и другая личность блокируются.
  Требуется GitHub CLI 2.81+ (машинный `auth status --json hosts` без токена появился в 2.81); вход не запрашивается при уже действующей сессии.
- Проверенное предложение передаётся через Git Data API как `request.json`
  в отдельной ветке `xrs-submissions/<uuid>`. Не создаётся PR, не изменяется main.
  До публичной загрузки выполняется локальная структурная проверка и требуется
  подтверждение отсутствия персональных данных/публичности отправки.
- Снимок содержит канал, ID владельца, срок действия, ожидаемую версию/sequence/hash
  каталога и предложения существующего формата. Максимум 50 предложений и 2 MiB
  канонических данных; branch tree содержит ровно один data blob.
- При повторной подготовке того же request ID проверяются прежний commit и hash.
  Перезапись существующего запроса запрещена. Отдельный immutable attempt ref
  `xrs-dispatches/<uuid>` предотвращает скрытый повторный dispatch после сбоя.
- Workflow запускается на main через API. Его validate job без signing secret
  получает data blob через API и проверяет точный SHA/структуру/базу. Код ветки
  данных не checkout-ится и не исполняется.
- Перед подписью повторяются получение и проверка того же снимка, актуального
  подписанного каталога, версий и служебных полей. При изменении базы выпуск
  блокируется. Существующие package format/Ed25519/history/release logic сохранены.
- Подтверждение Environment через API требует действующего user context владельца,
  `current_user_can_approve`, успешного validate и явного подтверждения точных
  run ID, workflow SHA, hash, канала и будущей версии. Обход Environment не добавлен.
- `approval-record.cjs` связывает подтверждение GitHub с точным запросом и SHA
  workflow; `publish.cjs` отвергает несовпадающую привязку перед упаковкой.
- Новый одноразовый административный процесс `scripts/publisher-admin.cjs`
  принимает только ограниченные команды JSON по stdin. Он не открывает TCP-порт,
  не принимает произвольные shell/API-команды и не возвращает credentials.

Статусы честно разделены: prepared, submitted, awaiting-workflow,
approved-awaiting-publication, workflow-succeeded, failed. Даже успешный workflow
сам по себе не возвращается как «Опубликовано»: UI должен дополнительно проверить
реальный подписанный Release/версию. Финальная проверка публичных файлов уже
присутствует внутри release.cjs, но независимая клиентская проверка ещё нужна.

## Как это будет работать для владельца

Первоначально: запустить один мастер на административном Windows-компьютере,
пройти официальный вход GitHub и отдельно разрешить setup ключей/Secret/корня.
Автоматизация не должна просить вручную редактировать JSON/PEM. Публичный корень
и инфраструктура могут потребовать одноразовый PR согласно защите main.
Обычная редакция медицинского шаблона такого PR не требует.

Далее после этапа C: «Редактировать → Проверить → Опубликовать», с явным
подтверждением Stable и версии в XRS. Ни GitHub web, ни ручной workflow dispatch,
ни отдельный APPROVE PR не нужны для каждой правки. Нельзя обещать бессрочный
доступ: при отзыве/истечении авторизации нужен повторный официальный вход.

**Сейчас эти кнопки ещё не подключены к новому backend в XRS.**
Этап B не включает завершённый интерфейс C или доставку двумя Windows-клиентами F.

## Запуск проверок и ограничения оператора

Для проверки без настройки производства:

```text
npm ci --ignore-scripts
npm test
npm run validate
```

В Windows `Setup-XRS-Templates.cmd --preflight-only` безопасно проверяет launcher
и инструменты без входа, генерации ключей и записи Secrets. Полный мастер не
запускался в этой задаче; его запуск с production keys требует отдельного решения.

`publisher-admin.cjs` — внутренний адаптер для будущего Electron main process,
а не дополнительная ежедневная команда врача. Его операции: authorize, stage,
dispatch, status, approve. Контракты и поведение проверены на фиктивном API.
Синтетические tests не передают фиктивные signing keys в GitHub.

## Что проверяется

`tests/simplified-publishing.test.cjs` покрывает:

- keyring / plaintext / env credential / чужую личность / JSON auth error;
- реальную схему предложения до отправки в публичное хранилище;
- data-only Git tree, неизменяемость ID/hash, отсутствие записи main/создания PR;
- неправильный commit/hash/channel, неизвестные файлы и истечение request;
- несовпадающую базовую версию/sequence/hash;
- отдельное подтверждение Stable, привязку review к run/hash/version/workflow;
- API 403, отсутствие права review и неуспешный validate;
- отсутствие повторного dispatch после известного запуска/неопределённой попытки;
- stdin, HTTP 204, запрет debug и безопасные ошибки без содержимого credentials;
- ограниченные команды stdio и запрет произвольной shell/API-операции;
- получение data blob, реальную валидацию предложения и подпись/чтение `.xrszip`
  существующим Ed25519-протоколом на временных синтетических ключах;
- отказ при test/root key для Stable и несовпадении authenticated approval.

Прежние Windows ACL/USB/launcher/resume tests и 113 sources остаются в validate CI.
Проверка реального Windows Credential Manager с авторизацией владельца не выполняется
обычным CI: он использует фиктивную auth metadata, не рабочие credentials.

## Оставшиеся блокировки

1. **Этап C:** подключить ограниченный stdio backend к существующему Electron
   main/preload и административному UI; обычные клиенты не получают публикацию.
   Не выдавать общую shell/API-обёртку renderer. Закрепить авторизацию за
   административным Windows-профилем и существующей локальной сессией.
2. **Подтверждение реальных прав:** интеграция пока не читает Environment Secrets,
   Variables и подробную защиту main (403). Нужен запуск мастера под владельцем
   с ожидаемыми правами, без передачи credentials в чат и обходов политики.
3. **Trust:** публичный root отсутствует; production keys не создавались.
   Подготовка backup/Secrets/публичного root делается только после разрешения.
   Доставку/сохранение последовательной ротации корня в XRS ещё нужно завершить.
4. **Этап D:** сохранить существующий updater и добавить сравнение конфликта
   локальной редакции с централизованной. Ни локальные правки, ни протоколы
   не должны переписываться.
5. **Этапы E/F:** реальная авторизация/review/pубликация Test через GitHub,
   установка на двух независимых Windows Electron, холодный запуск, offline,
   rollback и сохранность документов пока не пройдены.
6. При потере ответа dispatch и отсутствии видимого run система останавливается
   с DISPATCH_STATUS_UNKNOWN. Это безопасная остановка, а не автоматическое
   повторение. В UI требуется понятное восстановление/диагностика такого случая.
7. Staging в публичном репозитории делает шаблоны публичными; regex-проверка
   не гарантирует отсутствие всех видов ПДн. Нельзя отправлять пациентские отчёты.
   Автоматическое удаление старых data refs пока не реализовано.

Эти блокировки не снимаются успешным unit CI. Stable-публикация остаётся запрещена.
Следующий шаг — кодовое review кандидата этапа B и интеграция этапа C в отдельной
ветке приложения. Merge/активация production требуют отдельного разрешения.
