# XRS 0.4.84: публикация шаблонов и ограничение «не открывать GitHub»

Дата аудита: 25.11.2026. Статус: **BLOCKED для реализации полного сценария**.
Этап 1 выполнен. Рабочие ключи не создавались, защита не изменялась, публикация
и merge не выполнялись. Это архитектурное решение, а не реализованный сервис.

## Решение владельца и результат

Владелец отклонил вход в GitHub через системный браузер даже один раз за сессию.
Поэтому вариант GitHub App Device Flow, хотя он технически позволяет обойтись
без VPS, **не соответствует принятому пользовательскому сценарию**.

Не следует путать это ограничение с отсутствием API GitHub. Авторизованный
required reviewer может подтвердить ожидающий Environment через REST API.
Однако API не создаёт личность reviewer: для вызова нужен действительный
аутентифицированный контекст именно этого пользователя с нужными правами.
Локальный PIN XRS не является таким контекстом.

При одновременных условиях «не открывать GitHub для входа», «не сохранять
долгоживущие GitHub credentials в XRS», «не использовать доверенный внешний
посредник» и «сохранить подтверждение владельцем» безопасная полностью
автономная схема A/B **не установлена**. Генерация installation token внутри
Actions не решает идентификацию человека и не заменяет Required reviewers.
Существующие credentials интеграции Codex нельзя передавать в приложение.

## Проверенные возможности GitHub

1. GitHub App поддерживает Device Flow с публичным client_id, без client_secret
   в настольном приложении. Пользователь обязан подтвердить код на странице
   GitHub. Документированное время user access token — 8 часов; refresh token —
   6 месяцев. При таком варианте XRS должен отказываться от неистекающего токена,
   держать access token только в main-process memory и не сохранять refresh token.
   После завершения сессии/перезапуска потребуется новый вход. Этот вариант
   **отклонён владельцем**, поэтому вход не реализовывался и не запускался.
2. `POST /repos/{owner}/{repo}/actions/runs/{run_id}/pending_deployments`
   выполняет штатный review, а не bypass. Официальная таблица permissions
   подтверждает GitHub App user access token и `deployments:write`.
   Чтение ожидающих deployments требует `actions:read`; dispatch —
   `actions:write`. Доступ всегда ограничивается пересечением прав App и человека.
3. Успех зависит от реального required reviewer и политики GitHub. Нельзя
   подменять его bot identity, считать installation token подтверждением
   владельца, подтверждать от лица другого администратора или скрыто снимать gate.
   При prevent_self_review=true нужен отдельный допустимый reviewer.
4. Уведомление по почте, webhook или Actions OIDC само по себе не даёт локальному
   XRS права на публикацию. OIDC Actions удостоверяет job, а не владельца у врача.
5. Открытие GitHub внутри Electron webview, перенос cookies/credentials из другого
   приложения и использование PAT вместо согласованной авторизации не считаются
   решением поставленных ограничений.

## Сравнение вариантов

| Вариант | Действия администратора и GitHub | Секреты | Защита | Сложность и эксплуатация | Совместимость | Вывод |
|---|---|---|---|---|---|---|
| A: существующий GitHub workflow | Подготовить предложение; пройти существующее размещение/проверки и owner Environment review на GitHub | Подпись в защищённых Environments; клиенту всё равно нужна авторизация для автоматической отправки | Сохраняется при обычном review | Низкая/средняя; отдельного хостинга нет, действуют квоты/тарифы GitHub | Максимальная, но текущий workflow читает incoming/ из main | BLOCKED для режима без посещения GitHub |
| B: GitHub App + Actions | Войти через Device Flow в начале сессии; отправить предложение и отдельно подтвердить точный run/хеш в XRS | Только краткоживущий user token в RAM; signing keys остаются в GitHub | Может сохранить owner review через штатный API; PIN недостаточен | Средняя; VPS и постоянно работающий сервис не нужны; квоты GitHub сохраняются | Переиспользует издатель и updater; нужен клиент авторизации и безопасная передача предложения | Технически перспективен, но отклонён владельцем из-за входа на GitHub |
| C: управляемая функция-посредник + внешний вход | Войти через согласованный IdP/Windows SSO; отправить и утвердить в XRS; GitHub не нужен в ежедневной работе | Сервисные credentials только в secret manager; reviewer grant отдельно и строго привязан к владельцу; подпись в GitHub | Возможна после отдельной проверки модели; bot не заменяет reviewer | Выше; VPS можно не арендовать, но это внешний backend, обслуживание и тарификация функции/хранилища/IdP | Сохраняет текущий пакет, издатель и установку; добавляет только авторизацию и транспорт предложений | Единственный из рассматриваемых путей для дальнейшего проектирования при текущем UX; ещё не выбран и не реализован |

Нулевую стоимость C гарантировать нельзя: она зависит от существующего IdP,
поставщика, квот и хранения секретов. Даже C потребует первоначальной настройки
GitHub владельцем. Если запрещена и она, нельзя обещать сохранение GitHub owner
review без какого-либо исходного доверенного GitHub grant.

## Минимальный план реализации при согласовании допустимой модели

### Если в будущем разрешён B

- Зарегистрировать отдельную GitHub App только для XRS-Templates, включить Device
  Flow и expiring user tokens. Публичные client_id/repository_id — конфигурация;
  private App key для одного Device Flow в XRS не нужен. Новые права одобряет владелец.
- Права по операциям: contents для предложения/актива staging, actions для
  dispatch/status, deployments для review. Не запрашивать administration, workflows
  write, bypass main или доступ к основному репозиторию приложения без необходимости.
- Делать sign-in в main process; проверять числовой GitHub user ID, доступ к нужному
  репозиторию и фактическое право review. Не передавать токены renderer.
- Передать каноническое предложение в карантин GitHub (например, отдельный draft
  Release asset) с ограничением размера, точным SHA-256 и request ID. Не помещать
  большие медицинские документы прямо в workflow_dispatch inputs.
- Единожды согласовать изменение существующего publisher: читать строго указанный
  data asset вместо обязательного incoming/ на main. Это изменение входа текущего
  процесса, не второй updater. Код workflow остаётся защищён main и validate;
  для каждого изменения медицинских данных не требуется новый merge исходников.
- Проверить JSON/schema/privacy/base version/ID на неизменном снимке. Показать
  владельцу содержимое, channel, SHA предложения и SHA workflow/run. Выполнить
  отдельное явное подтверждение Environment через штатный review API, только если
  GitHub сообщает current_user_can_approve. Не auto-approve по нажатию «Отправить».
- Сохранить проверку реальной review identity в signing job, immutable releases,
  подписи, status Active/Archived и проверку публичной доступности после выпуска.

### Для C при действующем запрете входа на GitHub

- Сначала выбрать доверенный внешний IdP и управляемую функцию (например,
  Functions + secret manager); не разворачивать VPS или сервер клиники.
- Утвердить привязку внешней личности именно к GitHub required reviewer. Один
  только App installation token не даёт функции права выдавать bot за владельца.
- Если нужен owner user grant/refresh credential, однократно получить его штатным
  путём и хранить только на сервисе с шифрованием, отзывом, аудитом и ограниченными
  правами. Это отдельное решение владельца, а не автоматически разрешённый PAT.
- Сохранять явное действие владельца для конкретного proposal hash/channel/run;
  остальные пользователи остаются в ожидании. Не делать автоматический review
  от владельца для любого запроса, прошедшего локальный PIN.
- Передавать данные в тот же существующий publisher и пройти те же проверки,
  которые перечислены для B. Никакого ослабления main/Environment не требуется
  для самого протокола; достаточность конкретной делегации ещё нужно испытать.

## Приёмка и блокировки

Нужно отдельно согласовать допустимую авторизацию и процедуру ключей. Затем
подготовить реализацию, провести CI, получить отдельное разрешение на необходимый
merge инфраструктурного PR и настроить изолированный test channel. Проверить
реальное медицинское утверждение, API review от допустимого человека, подпись,
Active → Archived, два независимых XRS, offline/restart и откат. Нельзя считать
локальную симуляцию GitHub или успешный CI доказательством этого сквозного теста.
